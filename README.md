# cveta2

Командная утилита и Python-библиотека для работы с разметкой в CVAT. Выгружает
bbox-аннотации проекта в CSV, скачивает изображения из S3, создаёт задачи из готового
датасета, конвертирует разметку в YOLO и COCO, проверяет датасет и публикует его
в ClearML.

## Установка

Нужен Python 3.12 или 3.13. Пакет ставится из git-репозитория по тегу версии:

```bash
uv add git+ssh://git@<host>/<org>/cveta2@vX.Y.Z
pip install git+ssh://git@<host>/<org>/cveta2@vX.Y.Z
```

Или из собранного файла:

```bash
pip install cveta2-<версия>-py3-none-any.whl
```

Сабмодулей у репозитория нет, поэтому подойдёт любое зеркало или внутренний git-хост.
Зависимости берутся с PyPI или внутреннего индекса.

Подготовка и публикация датасетов (`verify --bundle`, `upload-dataset`, подкоманды
`dataset`) работают с ClearML и требуют extra `clearml`. Исключения — `dataset list`
и `dataset diff` для локальных папок и CSV: им ClearML не нужен. Установка с extra:

```bash
uv add "cveta2[clearml] @ git+ssh://git@<host>/<org>/cveta2@vX.Y.Z"
```

`fetch`, `fetch-task`, `upload`, конвертация и обычная проверка CSV работают без него.

Новая версия выходит автоматически, когда в ветку `main` сливают исправления или новые
возможности, поэтому обычно пакет ставят по тегу. Изменения, которые ещё не вошли ни в одну версию, можно
поставить по хешу коммита из `main`:

```bash
uv add git+ssh://git@<host>/<org>/cveta2@<хеш-коммита>
pip install git+ssh://git@<host>/<org>/cveta2@<хеш-коммита>
```

Хеш фиксирует установку: ветка `main` меняется, а коммит остаётся тем же.
В команде с extra `clearml` тег заменяется на хеш так же.

## Быстрый старт

Подключитесь к CVAT и укажите, куда складывать изображения:

```bash
cveta2 setup
cveta2 setup-cache
```

Выгрузите проект — по ID, по имени или выбрав его из списка:

```bash
cveta2 fetch --project 123 -o output/
cveta2 fetch --project "Мой проект" -o output/
cveta2 fetch -o output/
```

В `output/` появятся четыре файла:

| Файл | Что в нём |
| --- | --- |
| `dataset.csv` | актуальная разметка завершённых задач |
| `obsolete.csv` | устаревшая разметка |
| `in_progress.csv` | разметка из задач, которые ещё в работе, их ожидающие удаления и пометки об изображениях, снова взятых в работу после удаления |
| `deleted.csv` | изображения, удалённые завершёнными задачами |

Судьбу изображения решают только завершённые задачи: удаление в задаче, которая
ещё в работе, не убирает изображение из `dataset.csv`, пока задача не завершится.
Если изображение удалено завершённой задачей, а более новая незавершённая задача
снова его содержит, оно уходит из `deleted.csv`, а его прежняя разметка ждёт в
`in_progress.csv` вместе с новой. Подробнее — в
[описании `fetch`](docs/cli.md#выгрузить-все-аннотации-проекта-cveta2-fetch).

Одна строка CSV — один bounding box. Состав и порядок столбцов задаёт
`cveta2.CSV_COLUMNS`. Их описание (на английском) — в
[docs/feature/fetch-and-partition.md](docs/feature/fetch-and-partition.md).

Отдельные задачи выгружаются командой `fetch-task`. Она пишет только `dataset.csv`
и `deleted.csv`:

```bash
cveta2 fetch-task -p 123 -t 456 789 -o output/
cveta2 fetch-task -p 123 -t "Партия 3" -o output/
cveta2 fetch-task -p 123 -o output/    # выбрать задачи из списка
```

Если чего-то не хватает, команда спросит это в терминале, а в конце напечатает
полный вариант с флагами, чтобы следующий запуск повторить без вопросов. Текстовые
поля помнят ответы прошлых запусков: стрелка вверх подставляет предыдущее значение.
Для скриптов и CI есть [неинтерактивный режим](docs/configuration.md#неинтерактивный-режим).

Что полезно знать заранее:

- Проект CVAT можно задать как ID, имя или `организация/имя`. Если имя подходит нескольким
  проектам, команда остановится и перечислит их ID.
- Выгружаются только прямоугольники. Полигон заменяется охватывающим его
  прямоугольником, остальные фигуры и треки пропускаются; обо всём этом команда
  предупреждает. [Подробнее](docs/cli.md#фигуры-при-выгрузке).
- Аннотации завершённых задач кэшируются локально и в S3-бакете проекта, поэтому
  повторный `fetch` не скачивает их заново. [Как устроен кэш](docs/images-and-cache.md#кэш-аннотаций-задач).
- `fetch --completed-only` берёт только задачи со статусом `completed` в CVAT, `--no-images` не скачивает
  изображения, `--raw` дополнительно сохраняет неразделённый `raw.csv` со всеми строками.

## Публикация датасета в ClearML

`fetch` ничего не публикует. Публикация состоит из трёх шагов, и между вторым и третьим
вы сами смотрите на результат.

1. Назначьте каждой строке выборку `train`, `val` или `test`. В этом сценарии cveta2
   выборки не назначает.
2. Подготовьте пакет: команда проверит разметку и изображения и сложит результат
   вместе с отчётами в новую директорию. На вход нужна директория полной выгрузки
   `fetch` со всеми четырьмя CSV; выгрузка `fetch-task` не подойдёт.
3. Просмотрите отчёты и опубликуйте пакет.

```bash
cveta2 verify output --bundle --output-dir prepared \
  --project CV/datasets --dataset-name reviewed \
  --api-url https://classes.example.org/api/classes \
  --local-root /data/images --s3-root s3://images/project \
  --accept-default-classes --accept-class-changes --non-interactive

cveta2 upload-dataset prepared
```

Здесь `--project` — проект ClearML, а не CVAT. В ClearML попадают только `dataset.csv`,
`dataset.yaml` и `tasks.yaml`; изображения остаются там, где лежат. Если после
подготовки что-то изменилось — файлы, изображения, классы, — `upload-dataset` откажется
публиковать, и пакет нужно подготовить заново.

`verify` годится и для обычной проверки одного CSV, без публикации:

```bash
cveta2 verify output/dataset.csv --profile cveta2 --output-dir inspection
```

По умолчанию это только отчёт. Исправленную копию команда пишет лишь с `--clean`,
исходный файл не меняется никогда. Все флаги и коды выхода —
в [описании `verify`](docs/cli.md#проверить-csv-и-подготовить-пакет-cveta2-verify).

### Датасет из нескольких источников

Когда один датасет собирается из нескольких проектов CVAT и готовых CSV в S3,
состав источников описывают один раз в общем файле, а дальше работают с датасетом
по имени:

```bash
cveta2 setup --project-config /shared/cveta2/project-config.yaml
cveta2 dataset fetch construction --output-dir fetched
# ваш скрипт читает fetched и пишет transformed.csv
cveta2 dataset prepare construction transformed.csv \
  --source fetched --output-dir prepared --clean
cveta2 dataset report-errors prepared
cveta2 dataset publish prepared
```

`prepare` сама делит изображения на `train`/`val`/`test` — по умолчанию 60/20/20, доли
задаются в общем файле — и сохраняет прежнее распределение при следующих сборках.
`report-errors` заводит issues в CVAT для ошибок, которые удаётся привязать к
конкретному кадру, `publish` публикует датасет в ClearML. `--clean` разрешает `prepare`
принять исправления и исключить отклонённые строки. Начать стоит с запуска без этого
флага в отдельную директорию: такой запуск ничего не исправляет и показывает замечания
в отчёте.

CSV-источник в S3 должен уже содержать столбцы аннотаций, а его изображения — быть
доступны локально. `--output-dir` у `prepare` должен лежать вне каталога `--source`.
Подкоманды `list`, `show` и `versions` показывают описанные датасеты и их опубликованные
версии, `diff` сравнивает локальные CSV или версии ClearML.
[Полный сценарий](docs/cli.md#управляемый-датасет-cveta2-dataset).

В `tasks.yaml` такого датасета сохраняются полные определения меток CVAT и записи
реестра классов. Снимок источников, сделанный до появления этих записей, для подготовки
и публикации не годится: повторите `dataset fetch`, преобразование и `prepare`. Ранее
опубликованное распределение изображений по выборкам при этом сохраняется.

## Python API

У каждой команды, работающей с данными, есть соответствующая функция:

```python
import cveta2

result = cveta2.fetch("my-project", output_dir="out")
print(result.dataset)
```

Остальное — в [docs/python-api.md](docs/python-api.md).

## Настройка

Настроек два файла. Личный `~/.config/cveta2/config.yaml` хранит учётные данные,
локальные пути, таймауты и число потоков. Общий файл проектов описывает сервер и
организацию CVAT, проекты, источники и правила сборки датасетов; путь к нему задаётся
через `cveta2 setup --project-config PATH` или переменную `CVETA2_PROJECT_CONFIG`.
Личные значения общих правил не переопределяют.

Старый конфиг, где проектные правила лежали в личном файле, требует миграции:
`cveta2 setup --migrate-config` показывает разделение и выполняет его после
подтверждения.

`cveta2 doctor` проверяет конфигурацию, наличие учётных данных AWS/S3 и права на
каталоги кэша. Это локальная диагностика: доступность серверов она не проверяет.

Формат файлов, переменные окружения, повторы запросов и параллельность описаны
в [docs/configuration.md](docs/configuration.md).

## Разработка

```bash
unset UV_PROJECT_ENVIRONMENT              # использовать .venv этого рабочего дерева
uv sync --locked
bash scripts/install-hooks.sh
uv run --locked task --exit-code fix      # автоисправления и форматирование
uv run --locked task --exit-code verify   # проверки кода и затронутые тесты
```

Хук перед коммитом запускает `verify` и не пропускает коммит, пока в рабочем дереве
есть изменения или новые файлы вне индекса. Сообщение коммита проверяется на формат
Conventional Commits.

Полная приёмка — `uv run --locked task --exit-code acceptance` на чистом коммите —
обязательна для PR, коммиты которого меняют версию (`feat`, `fix`, `perf`, ломающие
изменения). Она включает живые тесты, которые сами поднимают CVAT, MinIO и ClearML в
отдельном пространстве имён кластера `docker-desktop` и удаляют его по окончании; нужен
`kubectl` с этим контекстом. Если кластер недоступен, локальную работу можно продолжать,
но обязательная проверка и слияние ждут её успешного прохождения. Какие проверки нужны
остальным изменениям, описано в
[docs/development.md](docs/development.md#check-selection).

Задачи ведутся в Linear, изменения доставляются через PR в GitHub; слияние в `main`
выполняет человек, и оно автоматически выпускает версию, если коммиты её меняют.
Порядок работы описан в [docs/agents/issue-tracker.md](docs/agents/issue-tracker.md),
команды, проверки, коммиты и выпуск — в [docs/development.md](docs/development.md),
устройство кода — в [docs/architecture.md](docs/architecture.md) (всё на английском).

Поведение продукта описано в [docs/feature/](docs/feature/) (на английском); руководства
в `docs/` объясняют, как пользоваться cveta2. Изменение поведения обновляет и файл в
`docs/feature/`, и соответствующий раздел руководства.
