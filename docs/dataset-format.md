# Формат данных

На этой странице описаны файлы, которые cveta2 читает и пишет: CSV с аннотациями, файлы полной выгрузки и каталог подготовленного датасета. Флаги команд описаны на страницах команд, их список в [указателе](README.md), форматы YOLO и COCO описаны в [commands/convert.md](commands/convert.md).

## Строка CSV

Одна строка CSV описывает один bbox. Если на изображении пять bbox, у изображения пять строк. Общие поля изображения (имя, размер, задача (task)) в каждой из них повторяются.

Тип строки задаёт столбец `instance_shape`:

| Значение | Что означает строка |
|---|---|
| `box` | Один bbox. Заполнены метка (label) и координаты. |
| `none` | Изображение без аннотаций. Такая строка одна на изображение и задачу, столбцы bbox пустые. |
| `deleted` | Изображение, удалённое в CVAT. Такие строки есть в `deleted.csv`, в `raw.csv` и в `in_progress.csv` (отложенные и переоткрытые удаления, см. [ниже](#файлы-полной-выгрузки)). |

Полигоны из CVAT выгружаются как bbox: берётся прямоугольник, описанный вокруг вершин, и cveta2 пишет предупреждение. Фигуры других типов пропускаются с предупреждением.

Все CSV записываются в UTF-8, без столбца индекса.

## Столбцы CSV

Порядок столбцов всегда один и тот же. В Python он доступен как `cveta2.CSV_COLUMNS`.

| № | Столбец | Тип | Описание |
|---|---|---|---|
| 1 | `image_name` | строка | Имя файла изображения без каталогов, например `000123.jpg`. По этому имени cveta2 связывает строки одного изображения. |
| 2 | `image_width` | целое | Ширина изображения в пикселях. В строках `deleted` может быть `0`. |
| 3 | `image_height` | целое | Высота изображения в пикселях. В строках `deleted` может быть `0`. |
| 4 | `instance_shape` | строка | `box`, `none` или `deleted` (см. выше). |
| 5 | `instance_label` | строка | Имя метки (label) bbox. Пусто в строках `none` и `deleted`. |
| 6 | `bbox_x_tl` | число | X левого верхнего угла, в пикселях. |
| 7 | `bbox_y_tl` | число | Y левого верхнего угла, в пикселях. |
| 8 | `bbox_x_br` | число | X правого нижнего угла, в пикселях. |
| 9 | `bbox_y_br` | число | Y правого нижнего угла, в пикселях. |
| 10 | `task_id` | целое | ID задачи CVAT, из которой пришла строка. `convert --from-yolo` пишет `0`. |
| 11 | `task_name` | строка | Имя задачи. `convert --from-yolo` пишет `yolo`. |
| 12 | `job_stage` | строка | stage job, к которому относится кадр (frame): `annotation`, `validation` или `acceptance`. |
| 13 | `job_state` | строка | state этого job: `new`, `in progress`, `completed` или `rejected`. |
| 14 | `task_completed` | логический | `True`, если задача завершена ([completed task](../GLOSSARY.md)): каждый её job стоит на stage `acceptance` со state `completed`. |
| 15 | `task_updated_date` | строка | Время последнего изменения задачи в CVAT. |
| 16 | `created_by_username` | строка | Автор фигуры в CVAT, если CVAT его вернул. |
| 17 | `frame_id` | целое | Номер кадра в задаче CVAT. |
| 18 | `split` | строка | `train`, `val` или `test`. fetch оставляет столбец пустым. Заполняете вы или `dataset prepare` (см. [ниже](#split)). |
| 19 | `subset` | строка | Subset задачи в CVAT. |
| 20 | `occluded` | логический | Флаг «перекрыт» из CVAT. |
| 21 | `z_order` | целое | Порядок отрисовки из CVAT. |
| 22 | `rotation` | число | Поворот bbox в градусах из CVAT. Для полигонов `0`. |
| 23 | `source` | строка | Источник фигуры в CVAT, например `manual`. `convert --from-yolo` пишет `yolo`. |
| 24 | `annotation_id` | целое | ID фигуры в CVAT. |
| 25 | `confidence` | число | Уверенность модели. fetch оставляет пустым. `convert --from-yolo` заполняет его из шестого поля строки YOLO, если оно есть. |
| 26 | `issue_text` | строка | Тексты issue CVAT на этом кадре (см. [ниже](#столбцы-issue)). |
| 27 | `issue_state` | строка | Состояния этих issue (см. [ниже](#столбцы-issue)). |
| 28 | `s3_image_path` | строка | Ключ объекта изображения в S3 (см. [ниже](#имя-и-пути-изображения)). |
| 29 | `image_path` | строка | Абсолютный путь к изображению на вашем диске. |
| 30 | `attributes` | JSON | Атрибуты фигуры CVAT как объект JSON: `{"имя": "значение"}`. Пустой объект `{}`, если атрибутов нет. |

### Пустые ячейки

Пустая ячейка означает «нет значения». В строках `none` и `deleted` пусты все столбцы bbox и фигуры: `instance_label`, координаты, `occluded`, `z_order`, `rotation`, `source`, `annotation_id`, `confidence`. В строках `deleted` также пусты `split` и столбцы issue.

Когда в одном файле есть строки `box` и строки `none`, целые столбцы с пустыми ячейками записываются как дробные числа: в файлах выгрузки вы увидите `z_order` = `0.0` и `annotation_id` = `78.0`.

### Координаты

Координаты задаются в пикселях исходного изображения. Начало отсчёта в левом верхнем углу изображения. `tl` — левый верхний угол bbox, `br` — правый нижний. Числа дробные.

### Атрибуты

`attributes` — объект JSON в одной ячейке. Ключ — имя атрибута CVAT, значение — строка. Русские символы пишутся как есть, без экранирования:

```csv
attributes
"{""цвет"": ""красный""}"
```

При создании задачи `upload` атрибуты не передаёт: в CVAT уходят только метка и координаты bbox.

### Столбцы issue

fetch собирает issue CVAT по кадру и пишет их в каждую строку этого кадра:

- в `issue_text` комментарии одного issue соединены через `; `, разные issue соединены через ` | `;
- в `issue_state` для каждого issue стоит `open` или `resolved`, через ` | `, в том же порядке.

Issues завершённой задачи берутся из кэша аннотаций. Issue, созданный или решённый после того, как задача попала в кэш, появится в CSV только после выгрузки с `--force` (см. [Кэш аннотаций](images-and-cache.md#когда-запись-используется)).

Если вы хотите, чтобы `upload` создал issue в новой задаче, поставьте в строке bbox `issue_state` = `new` и текст в `issue_text`. На каждый такой bbox создаётся отдельный issue с этим текстом. Полностью одинаковые строки (то же изображение, тот же текст, те же координаты) дают один issue. Строки без полного bbox пропускаются с предупреждением. Подробнее в [commands/upload.md](commands/upload.md).

### split

`split` — часть датасета для обучения: `train`, `val` или `test`. Другие значения не допускаются.

Split — ваш: cveta2 никогда не назначает его сам. Он только сохраняет опубликованный split изображения, которое уже опубликовано в родительской версии (`dataset prepare`, `verify <каталог>` и `upload-dataset`).

- fetch и fetch-task столбец не заполняют.
- Для `convert` и для подготовки каталога (`verify <каталог>`) split заполняете вы. `convert` останавливается с ошибкой, если у изображения split пустой или недопустимый.
- `verify <каталог>` заполняет пустые ячейки `split` у изображений, которые есть в родительском датасете (по `image_name`), их опубликованным split; ваши значения не меняются. Оставшийся пустой `split` разрешён и попадает в `pending` в `report.json`: его заполняете вы в подготовленном `dataset.csv`. Изображение родителя, которому вы сами вписали другой split, тоже попадает в `pending`. `upload-dataset` требует split у каждой строки, хотя бы одно изображение `train` и одно `val` и отказывается публиковать изображение родителя с другим split без `--force-resplit`.
- `dataset prepare` переносит опубликованный split по содержимому изображения (SHA-256) и записывает его поверх вашего значения; число замен — `split_replacements`. Split нового изображения берётся из вашего CSV; пустой split подготовку не блокирует, а попадает в `pending`. Если одно изображение (по SHA-256 содержимого, под одним или разными именами) стоит в нескольких split, подготовка блокируется: `Image content has rows in several splits: <имена>`.
- `convert --from-yolo` для датасета YOLO берёт split из раздела `train`, `val` или `test` его YAML. Для отдельных файлов предсказаний YOLO (без YAML) split остаётся пустым.

### Имя и пути изображения

- `image_name` — только имя файла. Если имя кадра в CVAT содержит подкаталоги (`2026-02/img.jpg`), в `image_name` остаётся `img.jpg`.
- `s3_image_path` — ключ объекта в бакете S3 проекта, без `s3://` и без имени бакета, с полным путём кадра. Если префикс хранилища пустой, ключ совпадает с именем кадра.
- `image_path` — абсолютный путь к файлу в кэше изображений ([image cache](../GLOSSARY.md)). fetch заполняет его, только если файл уже лежит на диске. Если файла нет, ячейка пустая. Где лежит кэш, описано в [images-and-cache.md](images-and-cache.md).

`upload` ищет изображения по `image_name` в каталогах поиска. Обязательны для него только столбцы `image_name` и `instance_label`.

## Файлы полной выгрузки

Полная выгрузка ([full fetch](../GLOSSARY.md)) — команда `fetch` по всем задачам проекта. Она пишет в каталог вывода четыре файла с одинаковыми столбцами и черновик `dataset.yaml`:

```text
output/
├── dataset.csv
├── obsolete.csv
├── in_progress.csv
├── deleted.csv
└── dataset.yaml
```

`dataset.yaml` — черновик ([dataset draft](../GLOSSARY.md)) для подготовки набора командой `verify`: назначение ClearML, API классов, исключённые классы и корни изображений, известные из конфигурации. Его ключи и предупреждения описаны в [fetch](commands/fetch.md#черновик-datasetyaml).

| Файл | Что в нём |
|---|---|
| `dataset.csv` | датасет ([dataset](../GLOSSARY.md)): строки последней завершённой задачи каждого изображения, которое не удалено и не переоткрыто. |
| `obsolete.csv` | устаревшие аннотации ([obsolete](../GLOSSARY.md)): строки завершённых задач, которые перекрыла более новая завершённая задача; все строки удалённых изображений; остальные завершённые строки переоткрытого изображения. |
| `in_progress.csv` | в работе ([in progress](../GLOSSARY.md)): строки незавершённых задач, перенесённые строки переоткрытых изображений, строки `deleted` отложенных и переоткрытых удалений. |
| `deleted.csv` | удалённые изображения ([deleted image](../GLOSSARY.md)): одна строка `deleted` на изображение. Если удалённых нет, в файле только заголовок. |

### Как строка попадает в файл

Решают только завершённые задачи. Задача считается завершённой, если `task_completed` = `True`. В старых CSV без этого столбца задача завершена, когда во всех её строках `job_stage` = `acceptance` и `job_state` = `completed`. Одна незавершённая строка делает незавершённой всю задачу.

Новее та задача, у которой больше `task_id`. Дата изменения не учитывается.

Для каждого изображения cveta2 делает так:

1. Находит самую новую завершённую задачу, в которой изображение есть как аннотация или как удаление. Если одна задача и разметила кадр, и удалила его, побеждает удаление.
2. Если в этой задаче изображение удалено, изображение удалённое. Все его строки идут в `obsolete.csv`, запись об удалении идёт в `deleted.csv`.
3. Исключение из шага 2: изображение переоткрыто, если более новая незавершённая задача держит его как обычный (не удалённый) кадр. Это переоткрытое удаление ([reopened deletion](../GLOSSARY.md)):
   - изображения нет в `deleted.csv`;
   - строки самой новой завершённой задачи, в которой кадр не удалён, переносятся в `in_progress.csv`;
   - остальные завершённые строки идут в `obsolete.csv`;
   - завершённая запись об удалении пишется в `in_progress.csv` строкой `deleted` с `task_completed` = `True`.
4. Если изображение не удалено, строки самой новой завершённой задачи идут в `dataset.csv`, строки более старых завершённых задач — в `obsolete.csv`.
5. Строки незавершённых задач неудалённого изображения идут в `in_progress.csv`.
6. Удаление в незавершённой задаче, которая новее завершённого результата, — отложенное удаление ([pending deletion](../GLOSSARY.md)). Оно ничего не решает, пока задача не завершена. Оно пишется в `in_progress.csv` строкой `deleted` с `task_completed` = `False`. Удаление старше завершённого результата не пишется никуда.

Задачи из списка игнорируемых задач ([ignore list](../GLOSSARY.md)) в выгрузку не попадают.

### Пример

Задачи 10 и 20 завершены, задача 30 в работе.

| Изображение | Задача 10 | Задача 20 | Задача 30 | `dataset.csv` | `obsolete.csv` | `in_progress.csv` | `deleted.csv` |
|---|---|---|---|---|---|---|---|
| `a.jpg` | bbox | bbox | — | строки задачи 20 | строки задачи 10 | — | — |
| `b.jpg` | bbox | удалено | — | — | строки задачи 10 | — | запись задачи 20 |
| `c.jpg` | bbox | — | bbox | строки задачи 10 | — | строки задачи 30 | — |
| `d.jpg` | bbox | — | удалено | строки задачи 10 | — | `deleted` задачи 30, `task_completed=False` | — |
| `e.jpg` | bbox | удалено | bbox | — | — | строки задач 10 и 30; `deleted` задачи 20, `task_completed=True` | — |

`d.jpg` — отложенное удаление: изображение остаётся в датасете, пока задача 30 не завершена. `e.jpg` — переоткрытое удаление.

## Выгрузка задач

`fetch-task` — выгрузка задач ([task fetch](../GLOSSARY.md)). Она пишет только два файла:

| Файл | Что в нём |
|---|---|
| `dataset.csv` | Все строки `box` и `none` выбранных задач, без разбиения на файлы. Сюда попадают и незавершённые задачи, если не указан `--completed-only`. |
| `deleted.csv` | Все записи об удалении из выбранных задач, без отбора по новизне. |

С `--save-tasks` обе команды, `fetch` и `fetch-task`, дополнительно пишут по файлу на задачу: `output/.tasks/task_<ID>.csv`. В нём строки `box` и `none` одной задачи. Для задачи без таких строк файл не создаётся.

## Сырой CSV

`fetch --raw` дополнительно пишет `raw.csv` — сырой CSV ([raw output](../GLOSSARY.md)). Четыре файла полной выгрузки пишутся как обычно.

В `raw.csv` все строки всех задач без разбиения: сначала строки `box` и `none`, затем строки `deleted` всех удалений. Столбцы те же.

## Подготовленный датасет

Подготовленный датасет ([prepared bundle](../GLOSSARY.md)) — каталог, который пишут `verify <каталог>` (подготовка каталога, [bundle preparation](../GLOSSARY.md)) и `dataset prepare` (управляемая подготовка, [managed preparation](../GLOSSARY.md)). Каталог пишется один раз:

- каталог не должен существовать заранее;
- каталог не должен лежать внутри исходного каталога выгрузки;
- `verify <каталог>` собирает каталог во временном каталоге рядом и переносит его на место одним переименованием, поэтому прерванная запись не оставляет ничего;
- у `dataset prepare` `preparation.json` появляется последним, поэтому прерванная запись не оставляет каталог, готовый к публикации.

Готовность (`ready`) означает: нет блокирующих проблем, нет структурных ошибок, и либо очистка не нужна, либо дано подтверждение очистки ([cleanup acceptance](../GLOSSARY.md)): у `verify <каталог>` и `dataset prepare` оно есть по умолчанию, пока не задан `--no-clean`. Подготовка также не готова, если у неисключённого класса нет ни одного bbox, а `dataset prepare` — ещё и если одно изображение (по SHA-256 содержимого) стоит в нескольких split. Условия split (пустой `split`, пустые `train` или `val`, нет bbox в `train`, у `verify <каталог>` — ещё другой split у изображений, опубликованных в родителе) подготовку не блокируют, а попадают в `pending` и проверяются при публикации.

### verify <каталог>

Источник — каталог полной выгрузки с четырьмя файлами.

```text
prepared/
├── sources.tar.gz
├── broken-images.csv
├── report.json
├── dataset.csv           только если ready
├── dataset.yaml          только если ready
├── tasks.yaml            только если ready
└── publication.json      после upload-dataset
```

`sources.tar.gz` — архив четырёх файлов выгрузки (`dataset.csv`, `obsolete.csv`, `in_progress.csv`, `deleted.csv`). Архив детерминированный: из одинаковых файлов всегда получаются одинаковые байты (фиксированные порядок, время и владелец). `preparation.json` этот вид подготовки не пишет. Контрольных сумм нет, и файлы `dataset.csv`, `dataset.yaml` и `tasks.yaml` можно править до публикации.

### dataset prepare

Источник — ваш преобразованный CSV и каталог managed fetch со `source-snapshot.yaml`.

```text
prepared/
├── transformed.csv
├── source-snapshot.yaml
├── broken-images.csv
├── report.json
├── dataset.csv           только если ready
├── dataset.yaml          только если ready
├── tasks.yaml            только если ready
└── preparation.json
```

Контрольных сумм у каталога нет. Файлы можно править после подготовки, например `dataset.csv` и `dataset.yaml`: `dataset report-errors` и `dataset publish` проверяют файлы такими, какие они сейчас. Каталог, у которого в `preparation.json` другой `format_version`, не читается: подготовьте датасет заново.

### Файлы каталога

| Файл | Назначение | Публикуется в ClearML |
|---|---|---|
| `sources.tar.gz` | Архив четырёх файлов выгрузки (только `verify <каталог>`). | да |
| `transformed.csv` | Точная копия вашего CSV (только `dataset prepare`). | нет |
| `source-snapshot.yaml` | Точная копия снимка источников ([source snapshot](../GLOSSARY.md)) (только `dataset prepare`). | нет |
| `broken-images.csv` | Исходные строки всех изображений, у которых хотя бы одна строка отклонена. Если у изображения отклонён один bbox, отклоняется всё изображение. | нет |
| `report.json` | отчёт проверки ([verification report](../GLOSSARY.md)) с итогом подготовки. | нет |
| `dataset.csv` | Очищенные строки датасета. | да |
| `dataset.yaml` | Назначение в ClearML, классы, API классов и разрешённые корни изображений. | да |
| `tasks.yaml` | список задач датасета ([task manifest](../GLOSSARY.md)). | да |
| `preparation.json` | Запись подготовки: имя датасета, родительский датасет, замечания к кадрам, `ready`, `clean`. Контрольных сумм нет (только `dataset prepare`). | нет |
| `publication.json` | Запись об успешной публикации (только `upload-dataset`). | нет |

При публикации ([publication](../GLOSSARY.md)) `upload-dataset` загружает в новую версию ClearML ровно четыре файла: `dataset.csv`, `dataset.yaml`, `tasks.yaml`, `sources.tar.gz`. Он проверяет файлы каталога такими, какие они сейчас: правки разрешены, если результат проходит проверки (см. [upload-dataset](commands/upload-dataset.md#как-это-работает)). `dataset publish` загружает три файла: `dataset.csv`, `dataset.yaml`, `tasks.yaml`. Он тоже проверяет текущие файлы каталога: правки разрешены, если результат проходит проверки (см. [dataset publish](commands/dataset.md#publish)).

Отличия двух видов подготовки:

| | `verify <каталог>` | `dataset prepare` |
|---|---|---|
| Копия входа | `sources.tar.gz` с четырьмя файлами | `transformed.csv` и `source-snapshot.yaml` |
| `preparation.json` | нет | всегда, `format_version: 3`, с полем `ready` |
| Правки перед публикацией | любые, если результат проходит проверки | любые, если результат проходит проверки |
| split | ваш; пустые ячейки у опубликованных изображений `verify` заполняет опубликованным split, `upload-dataset` не даёт его изменить без `--force-resplit` ([stable split](../GLOSSARY.md)) | ваш, из CSV; у опубликованных изображений `dataset prepare` записывает опубликованный, `dataset publish` не даёт его изменить без `--force-resplit` ([stable split](../GLOSSARY.md)) |
| Ключ `managed` в `dataset.yaml` и `tasks.yaml` | нет | есть |
| Публикация | `upload-dataset`, четыре файла | `dataset publish`, три файла |

### dataset.yaml

```yaml
clearml:
  project: Retail/Datasets
  dataset: retail-shelves
  output_uri: s3://my-bucket/.clearml
api_url: https://classes.example.com/classes
classes:
  bowl:
    prod_id: 1
    empty: false
    alt_names: []
images:
  local_root:
  - /home/user/data/images
  s3_root:
  - s3://my-bucket/images
```

| Ключ | Значение |
|---|---|
| `clearml.project`, `clearml.dataset` | Проект и имя датасета ClearML, куда `upload-dataset` публикует версию. Без них `upload-dataset` отказывается публиковать. |
| `clearml.output_uri` | Необязательно. Хранилище файлов версии, например `s3://my-bucket/.clearml`; без ключа ClearML берёт хранилище по умолчанию. |
| `api_url` | Адрес API реестра классов ([class registry](../GLOSSARY.md)). Только HTTP(S), без логина и пароля. |
| `classes` | Словарь: каноническое имя класса ([canonical class name](../GLOSSARY.md)) → описание. |
| `classes.<имя>.prod_id` | номер класса ([class identity](../GLOSSARY.md)). |
| `classes.<имя>.empty` | `true` для исключённого класса ([empty class](../GLOSSARY.md)). |
| `classes.<имя>.alt_names` | Старые имена класса. Они переписываются на каноническое имя. |
| `images.local_root` | Разрешённые локальные каталоги изображений. |
| `images.s3_root` | Разрешённые префиксы S3 вида `s3://bucket/prefix`. |
| `managed` | Только у управляемого датасета ([managed dataset](../GLOSSARY.md)): имя, хеш и копия описания датасета из общей конфигурации, адрес CVAT с организацией и назначенные split (`assignments`: хеш содержимого изображения → `train`/`val`/`test`). `dataset publish` пересчитывает блок из текущего `dataset.csv` и перезаписывает его в каталоге. |

Блок `clearml` пишет `verify <каталог>`.

### tasks.yaml

```yaml
included:
- 5
obsolete:
- 1
- 2
- 3
- 4
```

| Ключ | Значение |
|---|---|
| `included` | ID задач, чьи строки остались в очищенном `dataset.csv`. У `verify <каталог>` — только задачи, с которыми строки связаны в `sources.tar.gz` (пара `task_id` и `image_name` есть в его `dataset.csv`); `upload-dataset` строит `tasks.yaml` заново из текущего `dataset.csv` и перезаписывает его в каталоге. |
| `obsolete` | ID завершённых задач, которые полностью перекрыты: для каждого их изображения есть более новая завершённая задача или удаление. |
| `managed` | Только у управляемого датасета: снимок источников, с задачами, их временем изменения и признаком завершённости. `managed.parent_id` — родительский датасет; у первой версии (`--first`) — `null`. `dataset publish` строит весь `tasks.yaml` заново из текущего `dataset.csv` и перезаписывает его в каталоге. |

### report.json

`report.json` подготовки `verify <каталог>` — отчёт проверки и итог подготовки:

| Ключ | Значение |
|---|---|
| `blockers` | Блокирующие условия ([blocker](../GLOSSARY.md)). Пока список не пуст, `dataset.csv`, `dataset.yaml` и `tasks.yaml` не пишутся. |
| `ready` | `true`, если блокирующих условий нет. |
| `pending` | Условия split, которые нужно выполнить до публикации; правьте `split` в `dataset.csv`. |
| `destination` | `{"project": …, "dataset": …}`: куда собирались публиковать при подготовке. |
| `parent` | `{"id": …, "version": …}` родительского датасета ([parent dataset](../GLOSSARY.md)), который видел `verify`, или `null`, если его не было. `upload-dataset` сравнивает с ним последнюю версию. |
| `class_changes` | Добавленные и переименованные классы относительно родителя; без родителя все классы — добавленные. |
| `class_marks` | Классы, у которых отметка `empty` отличается от родителя: `[{"prod_id", "name", "empty"}]`. |
| `dropped_local_roots` | Локальные корни родителя, которых нет на этой машине: в новый `dataset.yaml` они не попали. |
| `broken_image_rows` | Число строк в `broken-images.csv`. |
| `split_prefilled` | Сколько изображений получили split родителя в пустые ячейки `split`. Изображение, у которого в другой строке уже стоит другой `split`, не заполняется. |

Остальные ключи — те же, что у отчёта проверки CSV ([verify](commands/verify.md)).

`report.json` подготовки `dataset prepare` тоже содержит `blockers`, `ready` и `pending`, а также `missing_classes` (классы без bbox), `split_collisions` (имена изображений, у содержимого которых строки в нескольких split), `mapped_findings`, `unmapped_errors` и `split_replacements` (см. [prepare](commands/dataset.md#результат)).

### publication.json

`upload-dataset` пишет его в каталог после успешной публикации. Хешей в нём нет.

| Ключ | Значение |
|---|---|
| `dataset_id`, `version` | ID и версия опубликованного датасета в ClearML. |
| `project`, `dataset` | Куда опубликовано. |
| `published_at` | Время публикации, UTC, ISO 8601. |

Если в каталоге уже есть `publication.json`, повторный `upload-dataset` печатает предупреждение с ID прежней публикации и продолжает. Обычно его раньше останавливает проверка родителя: прежняя публикация стала последней версией.

### preparation.json

Запись `dataset prepare`. Контрольных сумм в ней нет: она не привязывает каталог к содержимому файлов.

| Ключ | Значение |
|---|---|
| `format_version` | `3`. Запись с другим значением не читается: подготовьте датасет заново. |
| `name` | Имя управляемого датасета. |
| `parent_id`, `parent_version` | Последняя версия в ClearML при выгрузке: родительский датасет, а для первой версии с `--first` — версия, поверх которой начата управляемая история (родителем она не становится). `null`, если версий не было. |
| `findings` | замечания к кадрам ([feedback finding](../GLOSSARY.md)). |
| `ready` | Записаны ли публикуемые файлы. Только для сведения: `dataset publish` смотрит на сами файлы `dataset.csv`, `dataset.yaml` и `tasks.yaml`. |
| `clean` | Было ли подтверждение очистки: `true` по умолчанию, `false` с `--no-clean`. |
| `first` | Подготовлена ли первая версия управляемой истории (`--first`): `publish` создаст её без родителя. |
