# SIP-366 managed dataset flow, live pass, 2026-11-28

The page [managed-dataset-flow.md](../managed-dataset-flow.md) was checked against one run of the whole managed flow on the repository's live integration stand: CVAT, MinIO and ClearML in one Kubernetes session, with cveta2 at checkout `f238292` and ClearML SDK 2.1.12. The personal configuration, the caches and the ClearML cache directory pointed at a temporary directory. The session was stopped afterwards.

## What ran

A managed dataset with one CVAT source and one `s3-csv` source went through `dataset list`, `show`, `fetch`, `prepare`, `report-errors`, `publish`, a second `fetch`, a second `prepare` and `publish`, `versions` and `diff`. Two of the seeded CVAT tasks were completed before the first fetch. The transformed CSV held one deliberately broken CVAT row and one image with an empty split.

## What was observed

The first fetch wrote `dataset.csv`, `source-snapshot.yaml` and four tables under `sources/<name>/` for each source. The three extra tables of the `s3-csv` source held only the header line. No temporary sibling directory remained, nothing appeared in the ClearML cache, and no annotation cache directory was created. The snapshot recorded `parent_id: null`.

`dataset prepare` ended in each of its three ways. An existing output directory gave exit code 2 and wrote nothing. `--no-clean` gave exit code 1 and five files, with the blocker `Cleanup is needed and --no-clean was given.` The default run gave exit code 0 and eight files, with one pending line asking to fill the split of one image, and `preparation.json` recorded `parent_id: null` and `first: false`.

`dataset report-errors` created one CVAT issue, and a second run counted it as existing. The prepared directory was byte-identical before and after. The receipts file appeared under `managed-feedback/` beside the personal configuration, named by the SHA-256 of `source-snapshot.yaml`.

`dataset publish` created version `1.0.0` with no parent. In the prepared directory only `dataset.yaml` and `tasks.yaml` changed, no `publication.json` appeared, and no staging directory remained. The ClearML cache was still empty.

The second fetch recorded the published version as `parent_id`, reused the two completed tasks and read the five unfinished ones again. The ClearML cache then held one `<version id>.state.json` and two directories `ds_<version id>_<8 hex characters>`, each with `dataset.csv`, `dataset.yaml` and `tasks.yaml`. The first prepared directory could no longer be published: `Latest ClearML parent changed; fetch and prepare again`.

In the second cycle a published `val` image that the CSV marked `train` came back as `val`, and `report.json` counted one split replacement. Publication created version `1.0.1` with `1.0.0` as its parent. No second receipts file appeared, because the second cycle had no finding to deliver.

A second dataset definition started from a hand-made ClearML version without `dataset.yaml`. Its fetch result carried that version's ID as `parent_id`, and the ClearML cache gained a `.state.json` file but no `ds_` directory. `dataset prepare` stopped with `Parent <id> is not a managed dataset version; start a managed lineage with dataset prepare --first`. With `--first` it recorded that ID as `parent_id` with `first: true`, and publication created a version with no parent.

## What did not run

`s3-sync` resolved its target directory as `<images_root>/<CVAT project name>` and then failed, because the stand's storage endpoint is reachable only from inside the cluster. An interrupted write of the prepared directory, a legacy `feedback.json`, the CVAT project lookup of `dataset prepare` for image paths keyed by project name, a version larger than one ClearML chunk and `clearml.output_uri` were not exercised; the page describes them from the code.
