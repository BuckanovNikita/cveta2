# Конфигурация

## Личный и общий файлы

Настройки разделены по владельцу. Личный `~/.config/cveta2/config.yaml`
хранит учётные данные, локальные пути, таймауты и параллельность. Общий YAML
хранит сервер и организацию CVAT, проекты, источники, соответствия ClearML
и правила формирования датасетов. Личный файл не переопределяет общий.

Личный файл:

```yaml
schema_version: 1
project_config: /shared/cveta2/project-config.yaml
cvat:
  username: your-username
  password: your-password
  request_timeout: 300
image_cache:
  main: /data/images/main
cache:
  images_root: /data/images
  tasks_root: /data/task-cache
network:
  s3_workers: 16
  cvat_workers: 4
  retry_attempts: 5
  retry_max_wait: 30.0
upload:
  images_per_job: 100
  image_quality: 100
```

Общий файл, который можно использовать нескольким пользователям:

```yaml
schema_version: 1
cvat:
  host: https://cvat.example.org
  organization: team
projects:
  main:
    id: 12
    name: Main project
    sync_root: s3://images/main
    ignored_prefix: images/
    task_cache_s3: s3://cache/main
    ignore: []
  supplemental:
    id: 27
    name: Supplemental project
datasets:
  construction:
    sources:
      - name: main
        type: cvat
        project: main
      - name: supplemental
        type: cvat
        project: supplemental
      - name: imported
        type: s3-csv
        uri: s3://datasets/imports/annotations.csv
    clearml:
      project: CV/construction
      dataset: annotations
    api_url: https://classes.example.org/api/classes
    s3_roots:
      - s3://images/main
    empty_classes: []
    splits:
      train: 0.6
      val: 0.2
      test: 0.2
      seed: 42
    overlaps: {}
```

Имена `main`, `supplemental`, `construction` и имена источников — устойчивые
безопасные ключи. CVAT-источник ссылается на ключ из `projects`, где хранится
реальный ID. Несколько проектов могут входить в один датасет. Имена источников
внутри датасета, ссылки на источники и пары ClearML project/dataset не дублируются.
В общем файле нет паролей, токенов или локальных каталогов.

`sync_root`, `ignored_prefix`, `task_cache_s3`, исключения задач `ignore`,
`empty_classes`, `splits` и `overlaps` принадлежат общему файлу. Локальные
`images_root`/`tasks_root` и `image_cache` остаются личными. Явная команда
изменения общей политики записывает общий файл; при отсутствии прав она
завершается ошибкой, а не создаёт личное переопределение.

## Подключение и миграция

```bash
# Подключить существующий общий файл без повторного ввода учётных данных
cveta2 setup --project-config /shared/cveta2/project-config.yaml

# Или выбрать общий файл через окружение
export CVETA2_PROJECT_CONFIG=/shared/cveta2/project-config.yaml

# Проверить и разделить прежний смешанный конфиг
cveta2 setup --migrate-config
```

Подключение проверяет файл и сохраняет абсолютную ссылку в личных настройках;
общий файл не копируется и не редактируется. Обычный `cveta2 setup` настраивает
личные учётные данные и предлагает общий путь.

Старая конфигурация с проектными правилами требует миграции. Сначала показываются
пути, переносимые поля, соответствия и неоднозначности без секретов. Только после
подтверждения создаются защищённая резервная копия, общий файл и новый личный
файл. Существующий общий файл автоматически не перезаписывается. Отмена сохраняет
исходные данные; повторный запуск завершает прерванную подтверждённую активацию.
Имена проектов преобразуются в ID только по однозначным данным кэша обнаружения.
Неизвестные поля и неоднозначности требуют проверки; старые автоматические
настройки ClearML не превращаются в новые соответствия молча.

Неинтерактивный вызов не подтверждает миграцию автоматически: выполните её
отдельно. Простая старая конфигурация только подключения остаётся читаемой
для самостоятельных команд, пока не подключён общий файл.

## Пресет по умолчанию

Встроенный пресет задаёт исходные значения самостоятельных команд. Он не заменяет
выбранный общий файл и не переопределяет его проекты или правила.

## Приоритет источников

Личный файл: явный `--config` там, где он поддерживается → `CVETA2_CONFIG` →
`~/.config/cveta2/config.yaml`.

Общий файл: явный `--project-config` или аргумент Python API →
`CVETA2_PROJECT_CONFIG` → ссылка `project_config` в личном файле. Относительная
сохранённая ссылка разрешается от каталога личного файла; явный путь и переменная
окружения — от текущего каталога. Загружается ровно один общий файл.
Отсутствующий, недоступный или некорректный выбранный файл даёт ошибку без
скрытого отката к другому источнику.

Учётные данные и личные сетевые параметры сохраняют свои переопределения
окружением. Значения сервера/организации, конфликтующие с общим файлом, отклоняются.
Изменять проектные правила через личный файл нельзя, даже если значения совпадают.

## Переменные окружения

| Переменная | Назначение |
|---|---|
| `CVETA2_CONFIG` | Выбор личного файла |
| `CVETA2_PROJECT_CONFIG` | Выбор единственного общего файла проектов и соответствий |
| `CVAT_USERNAME`, `CVAT_PASSWORD` | Личные учётные данные CVAT |
| `CVAT_HOST`, `CVAT_ORGANIZATION` | Подключение самостоятельных команд; конфликт с общей идентичностью запрещён |
| `CVETA2_DATA_TIMEOUT` | Личный таймаут HTTP-чтения |
| `CVETA2_S3_WORKERS`, `CVETA2_CVAT_WORKERS` | Параллельность S3 и CVAT |
| `CVETA2_RETRY_ATTEMPTS` | Число попыток сетевого запроса |
| `CVETA2_NO_INTERACTIVE` | Ошибка вместо недостающего интерактивного решения |
| `CVETA2_DISABLE_CACHE` | Отключение кэша аннотаций |
| `CVETA2_RAISE_ON_FAILURE` | Завершать выгрузку при первой ошибке задачи |

## Ошибки сервера CVAT (5xx)

При выгрузке аннотаций (`fetch`, `fetch-task`) возможны временные ошибки сервера (HTTP 5xx) по отдельным задачам. По умолчанию такая задача **пропускается**: в лог пишется ошибка и контекст запроса, остальные задачи обрабатываются дальше. В лог также выводится готовая команда для добавления сломанной задачи в список игнорируемых — при следующем запуске она не будет запрашиваться:

```text
Чтобы пропустить задачу при следующем запуске: cveta2 ignore --project "имя_проекта" --add 123
```

Если нужно, чтобы вызов завершался при первой же 5xx (например, в CI), установите `CVETA2_RAISE_ON_FAILURE=true`.

## Параллельность передач

Файлы на S3 передаются параллельно — до `network.s3_workers` за раз, в обе стороны (загрузка и выгрузка). Задачи при `fetch` выгружаются до `network.cvat_workers` одновременно; issues и jobs при `upload` — тоже. Пул соединений S3 автоматически подстраивается под `s3_workers`.

Листинг больших хранилищ дополнительно разбивается по подпапкам первого уровня (`YYYY-MM/`) и обходится параллельно. Результат при этом побайтово совпадает с последовательным: порядок ключей сохраняется, потому что на него опирается разрешение одинаковых имён файлов.

`cvat_workers` намеренно меньше `s3_workers`: CVAT начинает ограничивать частоту запросов гораздо раньше, чем объектное хранилище, а каждый ответ 429 стоит паузы — то есть съедает тот же параллелизм, ради которого затевался. Если CVAT всё же отвечает 429, уменьшите `cvat_workers`.

## Повторы запросов и ограничение частоты (429)

Сетевые сбои и временные ошибки сервера повторяются автоматически: до `network.retry_attempts` попыток с экспоненциальной паузой (со случайным разбросом, чтобы параллельные воркеры не возвращались на сервер одновременно) и не дольше `network.retry_max_wait` секунд. Конечное неотрицательное число секунд в `Retry-After` задаёт паузу с тем же ограничением; отрицательное, неконечное, нечисловое значение или HTTP-дата оставляет обычную задержку.

Что именно повторяется, зависит от типа запроса:

| Запрос | Повторяется при |
|---|---|
| Чтение (список задач, аннотации, метаданные) | 429, 500, 502, 503, 504 и сетевых сбоях |
| Неидемпотентная запись (создание задачи, добавление аннотаций, issues) | только 429; ответ 503 не повторяется даже при `Retry-After` |
| Идемпотентная замена удалённых кадров или состояния job | 429, 500, 502, 503, 504 |

Разница намеренная. Ответ 429 означает, что запрос **отклонён** и на сервере ничего не изменилось, поэтому его безопасно повторить. 5xx на записи неоднозначна, в том числе 503 с `Retry-After`: CVAT мог применить изменение и не успеть об этом сообщить, а повтор загрузки аннотаций **добавит** второй набор bbox поверх первого (CVAT работает в режиме добавления, а не замены). Поэтому такая ошибка прерывает выгрузку, а не повторяется.

Если CVAT ограничивает частоту (429) и попытки исчерпаны, `fetch` **прерывается**, а не пропускает задачу: молча потерянная задача уменьшила бы датасет по причине, не связанной с её содержимым. Уменьшите `network.cvat_workers` и повторите запуск.

Для S3 отдельно повторяются коды `SlowDown`, `RequestTimeout`, `RequestTimeTooSkewed`, `InternalError` и `503`; ошибки доступа (403) и отсутствия объекта (404) не повторяются.

У CVAT SDK есть собственные повторы внутри HTTP-клиента. Их бюджет и ограничения
по HTTP-методам сохраняются; строки лога «попытка cveta2 N/M» считают только внешний
уровень и показывают паузу до следующей попытки. Это не суммарное число HTTP-запросов.
Для каждого запроса cveta2 копирует действующую политику SDK и меняет только
`raise_on_status`: последний ответ остаётся доступен после исчерпания повторов.
Общие настройки пула при этом не меняются. Поэтому исчерпанные 502/503/504 теперь
попадают под обычную политику 5xx задачи, а не превращаются в сетевую ошибку без статуса.
Проверка совместимости версии сервера SDK остаётся рекомендательной.

В ошибке указан фактически неудавшийся запрос: операция, HTTP-метод, очищенный URL,
доступные ID ресурсов, время UTC, статус, ID запроса/корреляции и краткое содержание
ответа. Это относится также к странице списка и чтению комментариев issue.
CVAT middleware добавляет `X-Request-Id`, когда ответ проходит через него;
по этому ID и времени ищите запрос в логах backend. Для 502/503/504 проверяйте
также proxy/ingress и доступность backend. Код ответа сам по себе не доказывает,
какой компонент сломан. См. [middleware CVAT](https://raw.githubusercontent.com/cvat-ai/cvat/develop/cvat/apps/engine/middleware.py).

Диагностика допускает только выбранные заголовки и идентификаторы query-параметров,
скрывает учётные данные, исключает cookies и сырой HTML, ограничивает текст ответа.
Автоматическое обследование сервера не запускается. Ошибки необязательного чтения
issues отдельно предупреждают о неполных данных; такие результаты не становятся
валидным кэшем завершённой задачи. Строгий режим относится к обязательным чтениям
задачи и не делает получение issues обязательным.


## Неинтерактивный режим

Для использования в CI/скриптах установите `CVETA2_NO_INTERACTIVE=true`. В этом режиме:

- Все интерактивные промпты заменяются на ошибки с подсказкой, какой флаг или переменную окружения нужно использовать
- Команды `setup` и `setup-cache` недоступны (у `setup-cache` работает только `--list`) — настраивайте через env-переменные или редактируя файл конфигурации напрямую
- При `fetch` без `--project` — ошибка (укажите `-p`); `fetch-task` может определить проект по числовому ID задачи, а для списка только из имён требует `-p`
- При `fetch-task` без `-t` или с `-t` без значения — ошибка (укажите `-t VALUE`)
- Если не хватает учётных данных — ошибка (задайте `CVAT_USERNAME`/`CVAT_PASSWORD`)
- Если путь к изображениям не настроен — ошибка (укажите `--images-dir`, `--no-images` или `image_cache` в конфиге)
- При `fetch` / `fetch-task` существующая выходная директория перезаписывается без вопросов; `verify` и подготовка датасета требуют новую директорию и отказываются перезаписывать существующую
- Команда `upload` требует явных `-p`, `--name` и `--labels` — без любого из них будет ошибка вместо интерактивного вопроса
- Команда `labels` доступна только с `--list` (редактирование меток интерактивно)
- Команда `ignore` без `--add`/`--remove`/`--list` недоступна (интерактивный TUI); `--add`/`--remove`/`--list` работают
- Команды `task drop-label` и `task delete` требуют флаг `--yes` (подтверждение недоступно)

Переменная может быть не установлена вообще — по умолчанию интерактивный режим включён.

```bash
# Пример CI-использования
export CVETA2_PROJECT_CONFIG="/shared/cveta2/project-config.yaml"
export CVAT_USERNAME="ci-bot"
export CVAT_PASSWORD="your-password"
export CVETA2_NO_INTERACTIVE=true

cveta2 fetch -p 123 -o output/ --images-dir /data/images
```

## Параметры проверки и публикации

Проверка CSV не требует CVAT или ClearML. Её профиль и параметры задаются в
`verify` либо `ValidationOptions`, а решения подготовки — через `verify --bundle`
или `PrepareOptions`: destination project/name, публичный API классов,
локальные/S3-корни, empty-классы, принятие новых классов и переименований, очистка.
См. [CLI](cli.md#проверить-csv-и-подготовить-пакет-cveta2-verify).
Это параметры конкретной подготовки, связанные локальной `preparation.json`.
Учётные данные ClearML и S3 берутся обычными SDK из окружения/их конфигурации;
они не записываются в payload или запись подготовки.

Автоматическая секция `clearml` с mappings и `CVETA2_CLEARML` больше не
поддерживаются. Старый файл конфигурации автоматически не изменяется; `fetch`
игнорирует эти настройки и не публикует данные. Команда `setup-clearml`, флаг
`--no-clearml` и keyword `publish_clearml` удалены. Для публикации используйте
отдельную подготовку и `upload-dataset` после просмотра результатов.
