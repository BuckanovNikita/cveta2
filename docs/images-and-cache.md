# Изображения, кэш и публикация

> Точное поведение описано в [feature/images.md](feature/images.md), [feature/annotation-cache.md](feature/annotation-cache.md), [feature/clearml-publication.md](feature/clearml-publication.md) и [feature/managed-datasets.md](feature/managed-datasets.md) (на английском). Это руководство объясняет использование и обновляется вместе с ними.

## Загрузка изображений из S3

При `fetch` cveta2 автоматически скачивает изображения проекта из S3 cloud storage, подключённого к CVAT. Используется **облачное хранилище проекта** (поле `source_storage` у самого проекта в API CVAT), а не хранилище отдельных задач. Все изображения ищутся в префиксе проекта по имени файла.

Источник скачивания можно переопределить через `projects.<ключ>.sync_root` общего конфига (значение — `s3://bucket/prefix` или просто `prefix` в бакете проекта). Переопределение действует на скачивание изображений при `fetch` и на `s3-sync`; загрузка (`upload`) всегда идёт в собственное хранилище проекта:

```yaml
projects:
  coco8-dev:
    id: 12
    name: coco8-dev
    sync_root: s3://other-bucket/mirrors/coco8
  my-other-project:
    id: 27
    name: my-other-project
    sync_root: some/other/prefix
```

### Где хранятся изображения

Для каждого проекта вы задаёте директорию вручную — через `cveta2 setup-cache` (настройка для всех проектов сразу) или при первом `fetch`. Пути хранятся в конфиге:

```yaml
image_cache:
  coco8-dev: /mnt/disk01/data/project_coco_8_dev
  my-other-project: /home/user/datasets/other
```

Если проект отсутствует в `image_cache`, но задан глобальный корень `cache.images_root`, используется `<images_root>/<имя_проекта>`. Эта подстановка работает у `fetch`, `fetch-task`, `s3-sync` и `upload`. Исключение — `convert`: он ищет изображения только по явным записям `image_cache` и путям из `--image-dir`, глобальный корень не подставляет. `--from-yolo` в режиме датасета не использует и их: изображения берутся из путей `dataset.yaml`.

Локальный кэш **повторяет структуру S3**: изображение сохраняется по своему ключу ниже префикса хранилища (`sub/img.jpg` → `<директория>/sub/img.jpg`). Общий `projects.<ключ>.sync_root` переопределяет корень (bucket/префикс) для скачивания, а настройка `projects.<ключ>.ignored_prefix` позволяет отбрасывать из полного S3-ключа только указанный верхний префикс, сохраняя больше иерархии. Например, при `ignored_prefix: data` ключ `data/projA/2026-01/img.jpg` сохранится как `<директория>/projA/2026-01/img.jpg`. Кэш рассчитан на нескольких пользователей: директории и файлы создаются с групповыми правами записи (0775/0664), а уже существующие пути можно привести к тем же правам командой [`cveta2 doctor --cache`](cli.md#починить-права-cveta2-doctor---cache). Старые «плоские» кэши (файлы в корне директории) новая версия не видит — изображения будут один раз скачаны заново в подпапки.

Имена кадров считаются относительными POSIX-путями внутри настроенного S3-префикса. Абсолютное имя принимается только когда оно находится под этим префиксом: корень отбрасывается, а остаток безопасно сохраняется внутри локального кэша. Пути с `..` и абсолютные пути вне префикса отклоняются.

Если осталось не более 2 000 незакэшированных изображений, cveta2 сразу делает GET
по ожидаемому S3-ключу без предварительного HEAD. Только ответ об отсутствующем
ключе запускает listing и поиск по имени файла. Для больших партий сначала
выполняется listing. Если все файлы есть по ожидаемым каноническим путям,
запросов к S3 нет.
Ошибки доступа, конфигурации и исчерпанные ошибки соединения при запросе прерывают
загрузку; обрыв тела ответа и ошибка локальной записи учитываются как неудачная
передача. Повторы и атомарная запись сохраняются: неполный файл не становится кэшем.

**Требование к именам изображений:** разные изображения должны иметь уникальные имена файлов, в том числе без последнего расширения, во всём проекте или датасете — независимо от директорий и разбиения на train/val/test. Недопустимы как два разных изображения `dir1/xxx.jpg` и `dir2/xxx.jpg`, так и пара `xx.jpg` / `xx.png`. Одно и то же изображение может повторяться в разных задачах и строках аннотаций. CSV использует `image_name` без директорий, а имена файлов разметки YOLO строятся без расширения изображения. Уникальность необходимо обеспечить во входных данных; автоматическое обнаружение таких конфликтов не гарантируется.

При поиске по имени файла итоговый S3-ключ и локальный путь берутся из найденного объекта. Например, кадр `img.jpg`, найденный как `prefix/month/img.jpg`, сохраняется в `month/img.jpg`; CSV содержит тот же ключ и абсолютный путь. Если имя кадра по-прежнему не совпадает с ключом, повторный запуск заново находит объект через отсутствующий канонический GET и listing (для больших партий — listing сразу). Найденный локальный файл повторно не скачивается.

### S3-креды

Для загрузки используется `boto3` со стандартной цепочкой авторизации — `~/.aws/credentials`, переменные `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`, IAM-роли. В конфиге cveta2 S3-креды не хранятся.

### Управление загрузкой

```bash
# Обычный fetch — изображения скачиваются (путь из конфига или интерактивный ввод)
cveta2 fetch -p coco8-dev -o output/

# Пропустить загрузку изображений
cveta2 fetch -p coco8-dev -o output/ --no-images

# Указать/переопределить директорию для изображений на этот запуск
cveta2 fetch -p coco8-dev -o output/ --images-dir /tmp/my-images
```

Уже скачанные файлы не загружаются повторно.

### Неинтерактивный режим и изображения

В неинтерактивном режиме (`CVETA2_NO_INTERACTIVE=true`) если путь для изображений не настроен — `fetch` завершается с ошибкой. Решение: укажите `--images-dir`, `--no-images`, или добавьте `image_cache.<project>` в конфиг.


## Кэш аннотаций задач

`fetch` и `fetch-task` кэшируют аннотации **по джобам**. В кэш попадают только
исходные фигуры джобов, которые находятся на `acceptance`/`completed`, и только если
CVAT сообщает дату изменения джоба: незавершённый джоб постоянно меняется и читается
из CVAT при каждом запуске. Статус задачи в CVAT на использование кэша не влияет.

При каждой выгрузке для каждой задачи заново запрашивается список джобов. Строки CSV
собираются заново из него и из закэшированных данных, поэтому `task_completed`,
`job_stage` и `job_state` всегда соответствуют текущим джобам. Запись джоба
используется, только пока совпадают дата изменения задачи (`task_updated_date`) и у
самого джоба его идентификатор, тип, диапазон кадров, этап (`stage`), состояние
(`state`) и дата изменения. Если джоб вернули на проверку или отредактировали, заново
читается только этот джоб. Изменение меток проекта сдвигает дату задачи, поэтому
перечитываются все её джобы. Если CVAT при сохранении аннотаций сдвигает и дату
задачи, перечитываются тоже все джобы этой задачи. Перечитывание только одного джоба
работает, когда меняются этап, состояние или дата самого джоба без изменения даты
задачи.

Метаданные кадров (включая удалённые кадры) и issues хранятся вместе с задачей в
записи `meta.json`. Она используется, пока не изменились дата задачи и весь набор
джобов (идентификаторы, типы, диапазоны, этапы, состояния и даты), и записывается,
только когда все джобы задачи завершены. Поэтому полностью закэшированная задача
стоит ровно одного запроса к CVAT — списка джобов. Если изменился хотя бы один джоб,
кроме его аннотаций заново читаются и метаданные кадров, и issues. Удаление кадра или
новый issue, которые не сдвигают ни дату задачи, ни дату джоба, до такого изменения
не видны: это осознанный компромисс ради одного запроса на задачу. После изменения
задачи в cveta2 (`task mark-deleted` и другие) её кэш сбрасывается полностью.

Если в задаче нет ни одной пригодной записи аннотаций, все её аннотации читаются
одним запросом и раскладываются по джобам. Иначе по отдельности читаются только джобы
без пригодной записи. Задачи с Ground Truth, consensus-джобами или пересекающимися
диапазонами кадров CVAT собирает особым образом, поэтому они кэшируются как одно
целое: одна запись `task.json` с аннотациями всей задачи. Она записывается, только
когда завершены все джобы задачи, включая Ground Truth, и используется, пока не
изменился ни один джоб.

Ошибка чтения issues выводит предупреждение, колонки issue остаются пустыми, а
`meta.json` не записывается: следующий запуск запрашивает метаданные и issues снова.
Завершённость в CSV сохраняется в `task_completed` и учитывает все джобы, включая
пересекающиеся и Ground Truth; старые CSV без этого поля проверяются по
`job_stage`/`job_state`.

Схема кэша аннотаций — 6: записи по джобам. Записи старого формата (один файл
`task_<id>.json` на задачу, схема 5 и раньше) не читаются и удаляются автоматически.
Локальные удаляются при первой выгрузке проекта после обновления, и в лог выводится
одна строка с их количеством. Старый объект задачи в S3 удаляется, когда для этой
задачи записываются новые записи; затрагиваются только ключи под префиксом кэша.
Коллега со старой версией cveta2, который пользуется тем же S3-зеркалом, после
этого перечитает такие задачи из CVAT. Вручную очищать кэш не требуется.
Предупреждения об аппроксимации полигонов выводятся, когда фигуры загружаются
из CVAT; при сборке строк из кэша они не повторяются. Предупреждение о фигурах без метаданных кадра выводится при каждой выгрузке.

Кэш живёт в двух местах:

- **Локально** — `~/.cache/cveta2/task_annotations/project_<id>/task_<id>/` с файлами `job_<id>.json` или `task.json` и `meta.json` (уважается `XDG_CACHE_HOME`). Корень можно сменить настройкой `cache.tasks_root` (глобально или по проектам). Локальный кэш тоже создаётся с групповыми правами (0775/0664) и чинится командой [`cveta2 doctor --cache`](cli.md#починить-права-cveta2-doctor---cache), но общим он будет только если `cache.tasks_root` указывает на общий каталог: путь по умолчанию лежит внутри домашней директории пользователя.
- **В S3-бакете проекта** — под ключом `<префикс проекта>/.cveta2_cache/task_annotations/task_<id>/` рядом с изображениями. Благодаря этому кэш общий для всех пользователей проекта: при локальном промахе запись берётся из S3 и сохраняется локально. Используется всегда исходное хранилище проекта в CVAT (переопределения `sync_root` на кэш не влияют). Поле `projects.<ключ>.task_cache_s3` общего файла переносит кэш в явное место: `s3://bucket/prefix` (можно другой бакет) или голый префикс в бакете проекта; записи при этом лежат под `<prefix>/task_annotations/` без сегмента `.cveta2_cache`.

Поведение:

- **`--no-cache`** — полностью отключить кэш на этот запуск (ни чтения, ни записи). Переменная окружения `CVETA2_DISABLE_CACHE=true` делает то же самое для всех запусков.
- **`--force`** — перечитать все задачи с CVAT и перезаписать кэш.
- Команды, изменяющие задачу (`upload`, `task mark-deleted`, `task drop-label`, `task delete`, `task status`), сбрасывают все записи кэша этой задачи — и локальные, и в S3-зеркале. `upload` очищает S3-зеркало, только если `task_cache_s3` задан полным адресом `s3://bucket/prefix`; зеркало по умолчанию в бакете проекта он не трогает.
- Полный `fetch` удаляет локальные записи задач, которых больше нет в проекте. Локальные записи исчезнувших джобов и джобов, вернувшихся в работу, удаляются при следующей выгрузке задачи.
- При обычной выгрузке ошибка S3 выводит одно предупреждение, и до конца запуска используется только локальный кэш.
- Невозможность создать S3-клиент (например, отсутствующий профиль AWS) при обычной выгрузке тоже даёт одно предупреждение и только локальный кэш; в `fetch --skip-validation` она прерывает запуск перед изменением jobs, если есть задача с jobs для принятия. Некорректное значение `task_cache_s3` завершает выгрузку ошибкой.
- В Python API сброс кэша после изменения задачи выбирает запись по тому же `Connection.config_path`, что и выгрузка.
- Сбой сброса кэша после успешного изменения задачи в CVAT или `upload` выводит предупреждение и не превращает команду в ошибку; если недоступно только S3-зеркало, локальная запись всё равно удаляется.

У `fetch --skip-validation` (API: `skip_validation=True`) сброс кэша перед
изменением jobs обязателен: используется `cache.tasks_root` выбранного проекта
из того же конфига, что и выгрузка, и настроенное S3-зеркало, включая
`task_cache_s3`. Локальная запись удаляется даже при `--no-cache`,
`CVETA2_DISABLE_CACHE=true` или API `cache="off"`; S3 при отключённом
кэшировании не затрагивается. Ошибка удаления прерывает запуск до первого
изменения этой задачи. Поэтому даже при частичном сбое обновления jobs
предыдущая запись не возвращает устаревшую завершённость.


## Публикация в ClearML

`fetch` сохраняет локальную выгрузку и выполняет обычные операции CVAT/S3;
автоматической публикации больше нет. Для публикации установите extra `clearml`
из выбранного Git-тега: `uv add "cveta2[clearml] @ git+ssh://git@<host>/<org>/cveta2@vX.Y.Z"`.
Локальная проверка CSV доступна без ClearML. Подготовка и публикация используют
обычную конфигурацию учётных данных ClearML и доступ к указанным S3-корням.

Назначьте split вне cveta2, затем выполните `cveta2 verify --bundle` над полной
выгрузкой. Просмотрите новую подготовленную директорию и позже вызовите
`cveta2 upload-dataset PREPARED_DIR` на той же машине. Детали аргументов —
в [CLI](cli.md#проверить-csv-и-подготовить-пакет-cveta2-verify).

Публикуются только `dataset.csv`, `dataset.yaml` и `tasks.yaml`; изображения,
исходные CSV и отчёты остаются локальными. Родитель — последняя finalized,
неархивная версия с точным совпадением ClearML project и dataset name. Старый
CSV-only родитель без метаданных блокирует подготовку: выберите новое имя датасета.
Родитель не изменяется, у дочерней версии удаляются унаследованные файлы и ссылки.
Успех означает синхронную загрузку, финализацию и проверку результата.

Перед публикацией повторяются проверка данных и изображений, доступность корней,
сверка классов и родителя, хешей payload и всех четырёх исходных CSV,
контрольной суммы `preparation.sha256` для байтов `preparation.json`. Изменённые
данные, решения или новый родитель требуют подготовки заново в другой директории.
При ошибке после создания дочерней версии сообщение содержит известный ID;
проверьте её состояние перед повтором. Ошибка не означает успешную финализацию.

Старые `setup-clearml`, `fetch --no-clearml`, keyword `publish_clearml`, секция
`clearml` с автоматическими mappings и `CVETA2_CLEARML` удалены без переходного
периода. Если в личном файле осталась секция `clearml`, команды завершаются ошибкой
с подсказкой `cveta2 setup --migrate-config`; файл без подтверждения миграции
не переписывается. `cveta2 upload` по-прежнему загружает данные в CVAT.

## Ошибки и безопасные пути

`s3-sync` проверяет полный список ключей и назначений до записи. Неканонические пути (например, `root//a.jpg`, `.` или `..`) и несколько ключей с одним назначением отклоняются; переименуйте такие объекты в S3 перед повтором. Только обычный файл считается попаданием в кэш: каталог на месте изображения даёт ошибку и не удаляется автоматически.

Повреждённый кэш аннотаций, который нельзя удалить или восстановить из-за прав доступа, считается недоступным: выдаётся предупреждение, чтение продолжается без него. Ошибки загрузки отдельных S3-объектов входят в счётчик `failed`, остальные передачи завершаются; ошибки доступа не повторяются безусловно.

При вычислении путей под `cache.images_root` небезопасные символы имени проекта кодируются; специальные компоненты `.` и `..` также не могут вывести путь за корень. Логическое имя проекта в CVAT, конфигурации и сообщениях не меняется. Обычные безопасные имена сохраняют прежнее написание каталога.

Полная выгрузка очищает устаревший кэш аннотаций по единому полному снимку ID задач,
полученному до фильтрации. Игнорируемые и незавершённые задачи не считаются удалёнными.
После `--skip-validation` снимок получается заново; удаление задачи после снимка
учитывается при следующем запуске. Файловые проверки путей при заполнении строк
выполняются один раз для каждого назначения за проход, сохраняя защиту от выхода
через символические ссылки.

## Источники управляемого датасета

`dataset fetch` отличается от самостоятельного `fetch`: он собирает полный
кандидат по общему определению, сохраняя снимки каждого источника. Метаданные
CVAT сравниваются с `tasks.yaml` последней версии; для неизменённых завершённых
задач аннотации не скачиваются. Изменения задачи или определений меток проекта
сбрасывают повторное использование; изменения реестра классов также требуют
обновления. Удалённые и открытые заново задачи учитываются по текущему состоянию.

Дополнительный `type: s3-csv` загружает один точный `s3://bucket/key.csv`.
Сохраняются контрольная сумма содержимого и доступные ETag/VersionId; ETag не
считается хешем содержимого. Изменённый CSV полностью заменяет прежний вклад
источника. Изображения не скачиваются: локальные файлы предоставляет пользователь
или его внешний скрипт до подготовки.

В опубликованном управляемом наборе остаются три файла. `dataset.csv` содержит
принятые обучающие строки; `dataset.yaml` — классы, корни и управляемую политику;
расширенный `tasks.yaml` — задачи, определения меток, все исходные разделы CVAT,
записи S3 CSV и отпечатки источников. Это позволяет использовать исходные данные
повторно, даже если скрипт или очистка исключили строки из обучения. ZIP не нужен.
Локальные отчёты и запись подготовки в ClearML не загружаются.

Перед публикацией повторно проверяются родитель, относящаяся к набору общая
конфигурация, источники, классы, изображения и подготовленные байты. Для ошибки,
которую можно однозначно связать с CVAT, создаётся review issue без изменения
разметки или статуса job. Ошибки доставки блокируют публикацию и допускают
продолжение; неадресуемые ошибки остаются локальными. Подробнее —
[управляемые команды](cli.md#управляемый-датасет-cveta2-dataset).

Начальный запуск поддерживается без существующего проекта или набора ClearML:
`fetch` и `prepare` сохраняют пустого родителя и ничего не создают удалённо.
Первая `publish` создаёт проект при необходимости и первую финализированную
версию без родителя. Следующий `fetch` использует её снимок источников.

Если создание review issue меняет время обновления задачи CVAT, текущая публикация
учитывает подтверждённое собственное изменение. Следующий `fetch` может один раз
перечитать такую задачу: опубликованный снимок сохраняет проверенные до отчёта
байты и исходное время задачи.
