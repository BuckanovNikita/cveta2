# Изображения, кэш и публикация

## Загрузка изображений из S3

При `fetch` cveta2 автоматически скачивает изображения проекта из S3 cloud storage, подключённого к CVAT. Используется **облачное хранилище проекта** (поле `source_storage` у самого проекта в API CVAT), а не хранилище отдельных задач. Все изображения ищутся в префиксе проекта по имени файла.

Источник скачивания можно переопределить через секцию `sync_roots` конфига (значение — `s3://bucket/prefix` или просто `prefix` в бакете проекта). Переопределение действует на скачивание изображений при `fetch` и на `s3-sync`; загрузка (`upload`) всегда идёт в собственное хранилище проекта:

```yaml
sync_roots:
  coco8-dev: s3://other-bucket/mirrors/coco8
  my-other-project: some/other/prefix
```

### Где хранятся изображения

Для каждого проекта вы задаёте директорию вручную — через `cveta2 setup-cache` (настройка для всех проектов сразу) или при первом `fetch`. Пути хранятся в конфиге:

```yaml
image_cache:
  coco8-dev: /mnt/disk01/data/project_coco_8_dev
  my-other-project: /home/user/datasets/other
```

Если проект отсутствует в `image_cache`, но задан глобальный корень `cache.images_root`, используется `<images_root>/<имя_проекта>`. Эта подстановка работает у `fetch`, `fetch-task`, `s3-sync` и `upload`. Исключение — `convert`: он ищет изображения только по явным записям `image_cache` и путям из `--image-dir`, глобальный корень не подставляет.

Локальный кэш **повторяет структуру S3**: изображение сохраняется по своему ключу ниже префикса хранилища (`sub/img.jpg` → `<директория>/sub/img.jpg`). Секция `sync_roots` переопределяет корень (bucket/префикс) для скачивания, а настройка `cache.projects.<проект>.ignored_prefix` позволяет отбрасывать из полного S3-ключа только указанный верхний префикс, сохраняя больше иерархии. Например, при `ignored_prefix: data` ключ `data/projA/2026-01/img.jpg` сохранится как `<директория>/projA/2026-01/img.jpg`. Кэш рассчитан на нескольких пользователей: директории и файлы создаются с групповыми правами записи (0775/0664), а уже существующие пути можно привести к тем же правам командой [`cveta2 doctor --cache`](cli.md#починить-права-cveta2-doctor---cache). Старые «плоские» кэши (файлы в корне директории) новая версия не видит — изображения будут один раз скачаны заново в подпапки.

### S3-креды

Для загрузки используется `boto3` со стандартной цепочкой авторизации — `~/.aws/credentials`, переменные `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`, IAM-роли. В конфиге cveta2 S3-креды не хранятся.

### Управление загрузкой

```bash
# Обычный fetch — изображения скачиваются (путь из конфига или интерактивный ввод)
cveta2 fetch -p coco8-dev -o output/

# Пропустить загрузку изображений
cveta2 fetch -p coco8-dev -o output/ --no-images

# Указать/переопределить директорию для изображений на этот запуск
cveta2 fetch -p coco8-dev -o output/ --images-dir /tmp/my-images
```

Уже скачанные файлы не загружаются повторно.

### Неинтерактивный режим и изображения

В неинтерактивном режиме (`CVETA2_NO_INTERACTIVE=true`) если путь для изображений не настроен — `fetch` завершается с ошибкой. Решение: укажите `--images-dir`, `--no-images`, или добавьте `image_cache.<project>` в конфиг.


## Кэш аннотаций задач

Завершённые задачи в CVAT на практике не меняются, поэтому `fetch` и `fetch-task` кэшируют их аннотации и при повторных запусках не скачивают заново. Кэшируются **только задачи со статусом `completed`**; запись действительна, пока `updated_date` задачи в CVAT совпадает с сохранённой — после любого изменения задачи она будет перечитана автоматически.

Кэш живёт в двух местах:

- **Локально** — `~/.cache/cveta2/task_annotations/project_<id>/` (уважается `XDG_CACHE_HOME`). Корень можно сменить настройкой `cache.tasks_root` (глобально или по проектам). Локальный кэш тоже создаётся с групповыми правами (0775/0664) и чинится командой [`cveta2 doctor --cache`](cli.md#починить-права-cveta2-doctor---cache), но общим он будет только если `cache.tasks_root` указывает на общий каталог: путь по умолчанию лежит внутри домашней директории пользователя.
- **В S3-бакете проекта** — под ключом `<префикс проекта>/.cveta2_cache/task_annotations/` рядом с изображениями. Благодаря этому кэш общий для всех пользователей проекта: при локальном промахе запись берётся из S3 и сохраняется локально. Используется всегда исходное хранилище проекта в CVAT (переопределения `sync_roots` на кэш не влияют). Настройка `cache.projects.<проект>.task_cache_s3` переносит кэш в явное место: `s3://bucket/prefix` (можно другой бакет) или голый префикс в бакете проекта; записи при этом лежат под `<prefix>/task_annotations/` без сегмента `.cveta2_cache`.

Поведение:

- **`--no-cache`** — полностью отключить кэш на этот запуск (ни чтения, ни записи). Переменная окружения `CVETA2_DISABLE_CACHE=true` делает то же самое для всех запусков.
- **`--force`** — перечитать все задачи с CVAT и перезаписать кэш.
- Команды, изменяющие задачу (`upload`, `task mark-deleted`, `task drop-label`, `task delete`, `task status`), сбрасывают локальную запись кэша этой задачи.
- Полный `fetch` удаляет локальные записи задач, которых больше нет в проекте.
- Проблемы с кэшем никогда не ломают выгрузку: при ошибке S3 выводится одно предупреждение, и до конца запуска используется только локальный кэш.


## Публикация в ClearML

Опциональная интеграция: после полного `fetch` (не `fetch-task`) все CSV-файлы из выходной директории публикуются как **новая версия ClearML Dataset**. Публикация происходит, только если выполнены все условия:

- установлен пакет `clearml` (в основные зависимости cveta2 он не входит) — он объявлен в extra `clearml`:
  `uv add "cveta2[clearml] @ git+ssh://git@github.com/<org>/cveta2.git"`;
- в конфиге секция `clearml` включена (`enabled: true`) и для проекта задан маппинг (см. `cveta2 setup-clearml`);
- не установлена переменная окружения `CVETA2_CLEARML=false` (разовое отключение).

Ошибки публикации никогда не ломают выгрузку — выводится предупреждение, результаты `fetch` не затрагиваются. Разово отключить публикацию можно флагом `cveta2 fetch --no-clearml`; в Python API у `cveta2.fetch` есть параметр `publish_clearml` (по умолчанию `True`).

Пример секции конфига:

```yaml
clearml:
  enabled: true
  projects:
    coco8-dev:
      clearml_project: "CV/coco8"
      clearml_dataset: "coco8-dev"
```
